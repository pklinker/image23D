# Phase 4 — Harden

Status per PLAN.md §8.4: **done**, scoped per explicit decisions made at the start of
this phase (see below) rather than PLAN.md's literal wording, which named things
(OIDC, tenancy) without specifying what either should actually mean here.

## Scope decisions made before starting

Three forks in PLAN.md's §4 wording were resolved with the user before writing code,
since getting them wrong would mean redoing real architecture later:

1. **Auth: API keys now, OIDC later.** PLAN.md's stack table says "OIDC (Entra/Okta)
   humans, API keys services." There's no real IdP tenant to wire up yet, and a stub
   OIDC flow against a fake issuer would prove nothing real. All `/v1/*` routes require
   an API key (`Authorization: Bearer ...`); OIDC is a follow-up once there's an actual
   Entra/Okta tenant.
2. **Single-tenant.** No `tenant_id` scoping anywhere. Auth is about *who* can act, not
   *which org's data* they see — there is one org.
3. **Include the `ComfyEmbeddedPipeline` swap in this phase**, even though it's an
   architecture change unrelated to auth/audit/retention/rate-limits. (In hindsight this
   was the highest-effort and highest-risk single item in the phase — see below.)

## Auth

- `common/models.py`: `ApiKey` (id, name, `key_hash`, timestamps, `revoked_at`).
- `common/security.py`: `i23d_<32 bytes url-safe>` tokens, SHA-256 hashed at rest — a
  fast hash is fine here because the token itself already carries 256 bits of entropy;
  there's no password-guessing surface a slow KDF would need to defend against.
- `api/app/auth.py`: `require_api_key` dependency. Reads `Authorization: Bearer`:
  `EventSource` (the SSE progress endpoint) can't set custom headers, so that one route
  also accepts `?api_key=` as a query param.
- `scripts/create_api_key.py`: bootstraps the first key by writing directly to Postgres
  — there's no authenticated way to mint the first key through an API that now requires
  one for every route.
- `/v1/api-keys` (create/list/revoke): any valid key can manage any other key. No
  admin/service scope split yet — fine for a small trusted team, a real gap before this
  is exposed more broadly.
- Viewer: API key entered once, stored in `localStorage`, sent as a header (query param
  for the SSE route). Storing a shared secret in browser-side JS is the known trade-off
  of "API keys now, OIDC later" applied to a human-facing UI — acceptable for an
  internal tool on a private network, not for anything internet-facing.

## Audit log

- `common/models.py`: `AuditLog` (actor, action, resource_type/id, `event_metadata`
  JSONB).
- Logged: `job.create`, `apikey.create`, `apikey.revoke`, `job.purge` (from retention,
  actor `system:retention`). Not logged: reads (`GET /v1/jobs/{id}`) — an audit log of
  every poll would be mostly noise; what matters is who created/destroyed what.

## Retention

- `settings.retention_days` (default 30). `worker/app/tasks.py::purge_old_jobs`, run
  daily via ARQ's `cron_jobs` (`worker_settings.py`, 03:00).
- Only touches jobs in a terminal state (`succeeded`/`failed`) past the window — a stuck
  `pending`/`running` job past 30 days is a bug to investigate, not something retention
  should quietly delete.
- Deletes the MinIO objects (input upload + all GLB artifacts) and the job row, and
  writes one `job.purge` audit entry per job with `age_days`.
- Verified by forcing `RETENTION_DAYS=0` and running the function directly against a
  real completed job: row deleted, MinIO artifacts gone, audit entry present.

## Rate limiting

- `api/app/rate_limit.py`: fixed-window counter in Redis, keyed by API key id + route
  bucket (`INCR` + `EXPIRE`). Applied to `POST /v1/uploads` (20/min) and
  `POST /v1/jobs` (10/min) — the two routes that cost real MinIO/GPU-queue resources.
  Fixed-window over a token bucket because the traffic this needs to catch is "a client
  bug retrying in a loop," not legitimate burst shaping; PLAN.md's own load assumption
  ("low volume ... concurrency = 1") means these limits are generous by construction.
- Verified: 20 calls succeed, the 21st (in the same 60s window) gets `429`.

## Migrations (added mid-phase, not originally planned)

Adding `Job.created_by` to the already-existing `jobs` table silently did nothing —
`Base.metadata.create_all()` (used since Phase 2) only creates tables that don't exist
yet, it never alters existing ones. `PHASE2.md` had already flagged this exact gap as
"worth adding before Phase 4"; this is that prediction landing. Added Alembic:
`alembic/` + `alembic.ini` at repo root, `alembic/env.py` wired to
`common.models.Base.metadata` and `common.settings.database_url`. The dev DB's few
smoke-test jobs were dropped (disposable test data, confirmed with the user) and an
autogenerated baseline migration replaces `create_all()` going forward. `docker/api.Dockerfile`
now runs `alembic upgrade head` before starting uvicorn.

## `ComfyEmbeddedPipeline`

PLAN.md §5 Phase 2 describes this as importing `nodes.NODE_CLASS_MAPPINGS` and hand-calling
each node in topological order, generating a first draft with `ComfyUI-to-Python-Extension`.
That would mean re-deriving the exact call contract of all ~30 distinct node classes by
hand — real reimplementation risk, the thing PLAN.md's Phase 1 design specifically
avoided by running on top of ComfyUI's HTTP API in the first place.

Before writing any code, a research pass read `execution.py`/`server.py`/`folder_paths.py`
directly (this ComfyUI build, `v0.34.0-56-g250b2e95`, is newer than training-data
knowledge of ComfyUI internals, so this had to be primary-source, not memory). Finding:
`execution.py`'s `PromptExecutor`/`validate_prompt` — the same engine ComfyUI's own HTTP
server calls — has no real dependency on the aiohttp app, websocket routes, or frontend.
It only needs a duck-typed object with `client_id`, `last_node_id`, and `send_sync(event,
data, sid)`. That meant embedding ComfyUI could reuse its actual executor/topological-sort/
validation code untouched, changing only the transport — not a rewrite of node logic.

### What changed

- `worker/app/embedded_pipeline.py`: `bootstrap_comfy()` (idempotent, runs once via ARQ's
  `on_startup` hook) sets `server.PromptServer.instance` to a `_StubServer`, then awaits
  `nodes.init_extra_nodes(init_custom_nodes=False, ...)`. `ComfyEmbeddedPipeline.run()`
  calls `execution.validate_prompt` then runs `PromptExecutor.execute()` in a worker
  thread (`asyncio.to_thread`) while the main coroutine drains progress off an
  `asyncio.Queue` the stub's `send_sync` feeds via `call_soon_threadsafe` — the same
  thread-bridging mechanism the real `PromptServer.send_sync` uses, not something
  invented for this stub.
- `worker/app/pipeline.py`: factored `load_patched_graph()` and `ProgressTracker` out of
  `ComfyHttpPipeline` so both backends share the graph-loading and stage-timing logic.
- **Containers merged.** Embedded execution needs ComfyUI's code, weights, and CUDA
  context in the *same process* as the job orchestration — they can no longer be separate
  containers talking over HTTP. `docker/gpu-worker.Dockerfile` replaces the old CPU-only
  `docker/arq-worker.Dockerfile`; `docker/worker.Dockerfile` (the plain ComfyUI HTTP
  server) survives only as an opt-in `dev` compose profile for interactively
  editing/exporting workflows through the real UI, same as PHASE1.md needed once.
  `ComfyHttpPipeline` still exists and still works as a fallback (`PIPELINE_BACKEND=http`),
  it just has nothing to talk to by default anymore.

### A second discovery, found only by actually running it: wrong event, not a wiring bug

The stub worked immediately — `send_sync` was being called, confirmed by direct
instrumentation. But the resulting jobs had **zero stage transitions and no early coarse
preview**, despite completing correctly with a valid final mesh. Diffing against Phase
2/3's real per-stage timing (both documented with actual numbers), the legacy
`"executing"` event this ComfyUI build's `execute()` free function sends (`execution.py:496`,
gated only on `client_id is not None`, which the stub sets) was never arriving. What *was*
arriving, ~80 times over one run: `"progress_state"` events from a different, newer
mechanism (`comfy_execution/progress.py`'s `WebUIProgressHandler`) — a cumulative
per-node `{node_id: {"state": "running"|"finished", ...}}` snapshot, not a discrete
start/stop stream.

`ProgressTracker` (in `pipeline.py`) now has two independent entry points feeding the
same stage-transition/on_artifact logic: `handle_executing()` for the HTTP backend
(unchanged, still what Phase 2/3 verified), and `handle_progress_state()` for the
embedded backend, which diffs each snapshot's `state == "finished"` nodes against a
`seen_finished` set to derive the same "this node just completed" signal from a
fundamentally different event shape. Root cause for why the two backends see different
events was not chased further (not our code to fix, and the HTTP path's own real-world
correctness across two prior phases stands on its own) — pragmatically, each backend
now uses whatever signal it actually receives.

## Verified (real jobs against the RTX 5060 Ti, both via curl and the actual browser viewer)

- Auth: unauthenticated request → 401; valid key → 200; revoked/bad key → 401.
- Rate limit: 20th call in a window succeeds, 21st → 429.
- Retention: forced 0-day window, job + MinIO artifacts deleted, audit entry written.
- Embedded pipeline, full run: stage transitions arrive on schedule
  (`segment_crop_fov` → `structure_coarse_mesh` → `shape_upsample` → `texture_sample` →
  `remesh_paint_final`), coarse GLB available well before completion, final mesh
  125,138 vertices / 249,916 faces with `COLOR_0` intact — matching Phase 3's tuned
  target and the HTTP backend's output.
- Full browser run (headless Chromium against the real containerized stack, API-key
  flow included): upload → coarse preview → final vertex-colored mesh, orbit controls
  working, no console errors.
